### Go / Ebitengine (전부 Go로 갈 경우)
- **ebitengine/oto 브라우저 백엔드 이슈 — 버퍼 크기 결정 어려움, ScriptProcessorNode 기반(deprecated, AudioWorklet 전환 예정)**: https://github.com/ebitengine/oto/issues/32
- 핵심 위험: Go wasm 런타임은 메인 스레드에 살고 goroutine 병렬성 없음 → GC/스케줄러가 오디오 글리치 유발 가능. 표준 Go 런타임은 AudioWorklet 스코프용 설계가 아님. TinyGo로 DSP만 워클릿에 올리는 경로는 선례 희박 → **스파이크 필요**
- Ebitengine wasm gzip 크기(수 MB) vs TS 앱(수백 KB) — 첫 소리까지 시간이 바이럴 퍼널 첫 관문
- 판정 계획: 스파이크 A(Ebitengine+oto 메인 스레드, 글리치 0·gzip ≤3MB면 전부 Go) / 스파이크 B(TinyGo DSP → AudioWorklet) / 폴백(DSP만 Rust 워클릿, 나머지 Go). 순수 Go `engine/` 패키지는 어느 갈래에서도 살아남음(네이티브 클립 렌더·스트림 호스트·게이트 공유)

**MilkDrop 프리셋 팩**은 커뮤니티 제작, 대부분 비공식 공유 → 저자·배포 조건 확인되는 것만 크레딧과 함께. Winamp 상표·스킨·로고 사용 금지.

## 12. 추가 실측 (2026-09-05 저녁)

### oto 브라우저 백엔드 — §6의 정정
- `ebitengine/oto` `driver_js.go` 실측: **AudioWorklet 노드를 쓰고 없을 때만 ScriptProcessorNode로 폴백**한다. 단 **샘플 생성은 메인 스레드**에서 하고 워클릿은 메시지로 받은 버퍼를 재생만 한다. 기본 버퍼 `8192 * channelCount` 바이트(채널당 2048 샘플, 48k에서 약 43ms) + 적응 버퍼링. 즉 "ScriptProcessorNode 기반"은 옛 정보였고, 핵심 위험(메인 스레드 GC·UI 부하 → 언더런, 50~100ms 지연)은 그대로다.
- TinyGo `-target wasm-unknown -gc=leaking -no-debug`로 JS 런타임 없는 순수 wasm을 만들 수 있다(공식 예제 hello-wasm-unknown). AudioWorkletGlobalScope는 `WebAssembly.instantiate`를 지원하므로 기술적으로 워클릿 안에서 돌 수 있다. **TinyGo+AudioWorklet 선례는 검색에 잡히지 않음** → 이틀 스파이크가 판정한다.
- Go 컴파일러는 arm64에서 `x*y+z`를 FMA로 융합하고 wasm은 융합하지 않는다 → 네이티브 vs 워클릿 렌더가 비트 단위로 다를 수 있다. `float64(x*y)+z` 명시 변환으로 융합을 막거나, 결정론 요구를 "같은 플랫폼 안"으로 낮춘다.

### 교차 리뷰 (3 리뷰어, `docs/reviews/`)
